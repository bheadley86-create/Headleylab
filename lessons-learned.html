How I Approach Troubleshooting

One of the biggest lessons from the lab has been to avoid changing multiple things at once. I try to isolate the problem, test one layer at a time, make a controlled change, and verify the result before moving on.

Plan → Build → Test → Troubleshoot → Verify → Document

Commands, logs, packet captures, service status, firewall rules, and repeat testing provide better evidence than assuming a configuration change worked.

Networking & DNS Lessons

DNS Can Fail While Connectivity Still Works

I learned that successful ping tests do not prove DNS is functioning. A client can have valid addressing and network connectivity while name resolution, authentication, or application access is still broken.

Troubleshoot in Layers

A consistent troubleshooting order makes network problems easier to isolate:

Addressing → Local connectivity → Gateway or route → DNS → Port → Service → Firewall → Application

VLAN Isolation Requires Intentional Exceptions

VLAN segmentation is most useful when communication between networks is controlled deliberately.

I configured an IoT VLAN with restricted access to the primary LAN while allowing required DNS traffic to the Pi-hole server over TCP and UDP port 53.

IPv6 Lessons

IPv6 Connectivity Does Not Prove a Service Is Reachable

During Pi-hole testing, a Windows client could successfully ping the server over IPv6 while DNS queries still timed out.

ICMPv6 connectivity proved addressing and Neighbor Discovery were working, but it did not prove TCP or UDP port 53 was permitted.

IPv6 Requires More Than Address Assignment

Working with IPv6 required understanding prefix delegation, Router Advertisements, SLAAC, RDNSS, ICMPv6, Neighbor Discovery, and host firewall rules.

Packet Capture Helps Identify the Failure Point

I used tcpdump to confirm that IPv6 DNS requests were reaching the Linux server.

Because the requests arrived but no DNS response returned, I narrowed the problem to the server rather than the router or switching path.

Port testing then confirmed that TCP 53 was blocked. Missing IPv6 UFW rules were added, and DNS began working.

Windows, Active Directory & Virtualization Lessons

Active Directory Depends on DNS

I learned that Active Directory authentication, Group Policy, and access to domain resources can fail even when a client has basic IP connectivity.

Checkpoints Make Testing Safer

Hyper-V checkpoints provided a safe way to test configuration changes, troubleshooting exercises, and recovery procedures without rebuilding a virtual machine every time something went wrong.

Local and Domain Context Matters

I practiced the difference between local and domain accounts and learned to verify which security context a user is operating under before troubleshooting permissions or access.

Linux & Server Administration Lessons

Check Service State Before Restarting

Commands such as systemctl status, logs, network listeners, and firewall rules provide useful evidence before restarting a service.

Display Commands and Configuration Commands Are Different

I learned to distinguish commands that show interface state from commands that actually change it.

Remote Access Should Be Verified Step by Step

When SSH, RDP, or PowerShell Remoting does not work, I verify reachability, listening ports, firewall rules, service status, and user authorization before assuming the remote-access tool itself is broken.

Security & Recovery Lessons

Least Privilege Reduces Risk

Administrative access should be used only when necessary.

I practiced removing unnecessary elevated access and verifying security settings rather than leaving accounts with more privileges than required.

Security Includes Knowing When Not to Trust a System

Malware removal does not always restore confidence in a system. Depending on the severity of a compromise, a reset, reimage, or clean installation may be safer.

System Restore Is Not a Complete Backup

Restore points can help recover certain system changes, but they do not replace proper backups, restore testing, and recovery planning.

Failures That Still Taught Me Something

Not every lab ended with a clean fix. I keep unresolved problems in my documentation because the troubleshooting process is still useful.

Windows Sandbox Troubleshooting

Investigated Windows Sandbox errors by reviewing Windows features, services, system files, container components, and related settings.

The issue was not fully resolved, but the process reinforced the importance of documenting attempted fixes and avoiding random changes.

Licensing and Activation

Investigated Windows activation and virtual-machine licensing issues and learned to separate licensing problems from networking, operating-system, or application failures.

Main Lessons Learned

  1. DNS is foundational. Working IP connectivity does not guarantee name-based services will function.
  2. Troubleshoot one layer at a time. Addressing, routing, DNS, ports, firewalls, services, permissions, and applications should be tested separately.
  3. IPv6 must be tested independently. IPv4 working correctly does not prove IPv6 services are configured correctly.
  4. Packet captures provide evidence. They can show whether traffic reaches a destination and whether the destination responds.
  5. Verification matters more than configuration changes. Logs, commands, service status, and repeat testing should prove the final state.
  6. Recovery should be planned before changes are made. Checkpoints and backups make experimentation safer.
  7. Least privilege reduces unnecessary risk. Administrative access should be limited to when it is required.
  8. Failed troubleshooting still produces useful experience. Symptoms, attempted fixes, errors, and final results are worth documenting.
  9. Documentation makes technical work explainable. Commands, screenshots, diagrams, packet captures, and notes make it easier to reproduce and discuss the work later.
